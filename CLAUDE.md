# CLAUDE.md

FluentComments replaces native WordPress comments with AJAX-driven,
spam-protected commenting. One PHP backend; three frontends (Svelte public UI,
Vue admin, React block). See README.md for the public API surface.

## Commands

```bash
pnpm run build        # i18n scrape + Vite + the block
pnpm run dev          # watch app.js + admin_app.js
pnpm run i18n         # rescrape $t() into app/Services/TransStrings.php
./build.sh            # release zip into builds/
php tests/SpamGuardTest.php   # and the seven others in tests/
```

Tests run standalone against a stubbed WordPress surface. No PHPUnit, no
Composer autoloader; every PHP file is `require_once`d in `fluent-comments.php`.

## Rules That Have Already Cost A Bug

1. **Never call `wp_insert_comment()`.** `CommentSubmission::handle()` is the
   only path into the database.
2. **`Frontend::renderCommentList()` and `CommentBlock.svelte` must stay
   identical** — two renderers over one array.
3. **Nothing visitor-specific in HTML, ever.** Assume the page is cached and
   served to somebody else.
4. **Never edit `app/Services/TransStrings.php`** — generated by `npm run i18n`.
5. **A literal hex in `resources/admin/src/style.scss` is a bug** — it survives
   into dark mode. Add a `--flc-*` token.
6. **One front end. Do not add a second.** A classic theme and a block theme
   render the same app; `app/Views/comments.php` is a two-line shim over
   `Frontend::renderApp()`. The PHP form, the comment walker and the second
   script that used to serve classic themes are gone — they were the same
   lifecycle written twice, and the second copy was the one that got forgotten.
7. **`PAYLOAD` in `build.sh` is a whitelist**, not an exclude list.
8. **A new script bundle must be listed in `Frontend::MODULE_HANDLES`**, or it is
   enqueued without `type="module"` and silently never boots.
9. **Do not vendor Emogrifier. Do not add a webfont.**

## Backend

`fluent-comments.php` boots on `plugins_loaded`, loads every PHP file manually,
registers the text domain on `init`. Namespace `FluentComments\App\*`.
`app/Hooks/hooks.php` calls `Frontend::register()` plus six handlers:
`CommentsHandler` (template override, enqueuing, the three public AJAX actions,
shortcode), `BlockHandler`, `AdminSettingsHandler` (admin page, setup notice),
`EmailSettingsHandler`, `CommentNotificationHandler` (who gets our three emails),
`CoreEmailHandler` (rewrites WordPress's two notices).

### One Submission Path

One path into the database — the most important constraint here. Everything
POSTs to `admin-ajax.php?action=fluent_comment_post` and hands a normalised
payload to **`CommentSubmission::handle()`**, which calls
`wp_handle_comment_submission()`. (Two front ends used to arrive here; they are
one app now, but the endpoint is still the only door and third-party callers
reach it too.)

**Never call `wp_insert_comment()` here.** It does not fire `comment_post`, where
core's moderation and post-author emails hook, and skips core's validation. An
earlier REST path did, and silently lost both.

`CommentSubmission` also enforces what core does not: a reply's parent belongs to
the same post, the thread is within `thread_comments_depth`, and a logged-out
commenter gave a name and valid email. **That last rule is ours and has no
switch** — deliberately absent from `DiscussionSettings::BOOLEANS` and the
settings screen, and `validateIdentity()` never reads core's
`require_name_email`. Reason: all three of our emails are addressed by
`comment_author_email`, so an anonymous comment opts its author out of the reply
notifications the rest of the thread gets. `resources/js/validate.js` is the same
rule client side; it saves a round trip, it never decides.

### Foreign Hooks Are Isolated

We render our own form and **do not fire core's `comment_form` hooks**, so a
plugin that would add a CAPTCHA field never renders one — and running its
validator anyway would reject every comment over a field that was never on the
page. So for the duration of the insert, `suppressForeignHooks()` strips
`preprocess_comment` and `pre_comment_on_post` to an allow list (Akismet only by
default), restoring them in a `finally`. Core registers nothing on either hook,
so only third parties are affected. Escape hatches, both rarely correct:
`allowed_comment_hooks`, `render_core_form_hooks`.

### Spam Protection (`SpamGuard`)

Scored, not pass/fail: a suspicious comment is **held for moderation**, only a
conclusive one is rejected (unbindable session +40, token younger than
`token_min_age` +40; `>= 30` holds).

- **Session cookie** `flc_sid` — HttpOnly, SameSite=Lax, set when a token issues.
- **Submission token** — `v3|issuedAt|postId|jti|sessionDigest|hmac`, signed with
  `wp_salt('auth')`, bound to that cookie and **single-use**. The cookie binding
  is what makes it a CSRF defence; the separate round trip alone would not be.
- **Honeypot** — field name derived from the site salt, different per install.
- **Rate limits** — tight per *session* (10/hr), loose per *IP* (100/hr). Keying
  the tight limit on the session stops a shared exit IP (a CDN, an office)
  putting the whole site in one bucket.

### Transport

Three public actions — `fluent_comment_session` (POST), `fluent_comment_post`
(POST), `fluent_comment_list` (GET, "load more" only; page 1 is in the document).
**They carry no nonce**; `SpamGuard` gates them. Admin actions under the
`fluent-comments-admin-` prefix are logged-in only and *do* use a nonce plus
`manage_options`, both via `Helper::verifyAdminAjax()`. That distinction is the
design: a nonce is fine on a screen that is never cached and fatal on one that is.

**The REST layer was deleted — do not reintroduce it.** A stale `wp_rest` nonce
in a cached document is a hard 403, not a downgrade, so a visitor who logged out
in another tab mid-compose lost their comment. Known cost: `admin-ajax.php`
defines `WP_ADMIN`, so **`is_admin()` is true** during a submit — watch for
third-party `comment_text` filters gating on `!is_admin()`.

### Caching Is a Hard Constraint

Assume every page is served from a full-page cache to somebody else.

- **Nothing visitor-specific goes into HTML.** It all comes from
  `Frontend::getSessionPayload()` via `fluent_comment_session`, never cached.
  The session is fetched **on intent, not on load**, so a reader costs zero
  uncached requests.
- **Neutral means undecided, not "the anonymous one".** The form renders no
  visitor-specific branch before the session names it — that is what made a
  signed-in commenter watch the name and email fields appear under them and then
  vanish. Unknown renders as nothing (`sessionResolved && !isLoggedIn`), and a
  session that *fails* resolves to the signed-out branch, which is the one that
  still lets somebody comment. Name and email come from the `comment_author_*`
  cookies, read in the browser (`readHashedCookie`), never printed into the page.
  Intent starts at `pointerenter`/`pointerdown` on the whole comment area rather
  than at focus, which is usually a whole round trip of head start. Still zero
  requests for a reader who never reaches for it.
- **`comment_registration` is the one branch rendered from `is_user_logged_in()`,
  and it is corrected rather than trusted.** There is no neutral form when login
  is required: a form is wrong for the reader who must log in, the notice is wrong
  for the member who need not, and withholding both costs a request on load from
  readers who will never comment. So the render-time guess goes into the markup —
  the same call core's `comment_form()` makes at
  `wp-includes/comment-template.php:2712` — as `must_log_in` / `login_message`
  on the bootstrap in `renderApp()` (**not** `getVars()`, which stays
  cache-safe by construction;
  `app.js` hands it to `seedRenderedLogin()` so a reply form created later opens
  with it too). The session stays the authority: the first `pointerenter` over the
  comment area — the notice included, since that is all a mis-served reader has to
  reach for — swaps the branch in either direction. Core has no such correction;
  it relies entirely on every page cache bypassing on `wordpress_logged_in_*`.
  A session that never answers leaves the rendered guess standing.
- **The first page of comments is server-rendered twice** by
  `Frontend::renderApp()`: into a `<script type="application/json">` block that
  `app.js` hydrates from, and as real HTML via `renderCommentList()`. The JSON
  avoids an uncached WordPress boot on every view; the HTML is for everything
  that never runs the script, since a `<script>` block is data, not content, and
  without it a crawler saw "Loading…". **The two renderers must match element for
  element** — `app.js` empties the container before mounting, so any disagreement
  is a visible reflow the moment the script runs.

### Block vs Classic

**Same app either way** — the difference is only how it gets onto the page.
`Helper::isBlockTheme()` / `isHandlingComments()` gate **rendering**. Classic:
`CommentsHandler` swaps `comments_template` for `app/Views/comments.php` and
enqueues on `wp_enqueue_scripts` — `renderApp()` enqueues too, but it runs after
`wp_head`, so hooking early is what keeps the stylesheet out of the footer and
the comment section from repainting. Block themes: nothing is placed
automatically; the user adds the block or the `[fluent_comments]` shortcode.

`comments_template()` runs its own comment query before our filter is reached
and nothing renders from it; `onlyApprovedComments()` keeps that query
visitor-independent anyway, since it still lands in `$wp_query->comments`.

`TemplateScanner` answers where it is missing, walking `get_template_hierarchy()`
then that template's blocks (following `core/template-part` and `core/pattern`,
with a seen-set). Shortcode detection uses `get_shortcode_regex([SHORTCODE])`,
not `has_shortcode()`, which would answer based on whether our `init` hook had
run. **Nothing is cached, and it runs only through `scan-templates`** on the
settings screen — a cached answer is worst exactly there, since the screen is
opened right after editing a template.

Whether a foreign submission is *rejected* is `willRejectNativeComments()`, and
that is deliberately **theme-independent**: selected post type +
`reject_native_comments` is the whole test. Consequence accepted knowingly — on a
block theme where the block is not yet placed, those posts take no comments at
all.

### The Setup Notice

No activation hook, so a fresh install has **no `_fluent_comments_settings` row**
and the defaults already hand `post` to FluentComments with
`reject_native_comments` on. `maybeShowSetupNotice()` runs on `admin_notices`
until they save once; `Helper::isConfigured()` is the whole test (the row
exists). **It is not dismissible, and that is the point** — a dismiss link would
let someone buy silence without seeing what the defaults are doing. **Keep it
cheap:** one autoloaded option and one user meta, no queries, since it renders on
every admin page.

## Emails

Five, one screen, `EmailService` the single definition. Three ours
(`comment_approved`, `reply_to_participants`, `new_comment_to_post_author`); two
are WordPress's own (`core_comment_notification`, `core_comment_moderation`),
which we filter rather than send.

**On/off is not stored in the email option.** Each already had a switch — three
keys in `_fluent_comments_settings`, plus `comments_notify` /
`moderation_notify`, which `Settings › Discussion` also writes. A second copy
would be a second answer, so `EmailService::TOGGLES` maps each email to its
existing switch and `status` is *composed*. The Emails list is the only place
they are switched, via `toggle-email`.

**Keep the two halves apart when writing.** `saveEmail()` takes `$enabled` and
`$contentStatus` separately — hence a switch plus a two-way radio, not one
three-way control. Folding them meant disabling an email also reset its content.

Statuses `system` / `active` / `disabled`. **`system` means different things on
either side of the list, deliberately** — for our three it renders our built-in
body through the same parser and template as `active`; for the two core ones it
means *leave WordPress alone*, because those notices predate the plugin and
turning a plain-text notice into HTML on upgrade is not a change anyone asked
for. `CoreEmailHandler` hooks core's `comment_notification_*` /
`comment_moderation_*` filters rather than replacing `wp_notify_postauthor()`, so
core keeps its recipient list and gating; scoped to FluentComments post types.

**Smartcodes.** `SmartCodeParser` fills `{{group.field}}` and `##group.field##`
from `comment`, `post`, `receiver`, `site`. **The delimiter decides the
escaping:** `{{}}` HTML-escaped, `##...##` attribute-escaped for an `href`,
`URL_KEYS` through `esc_url()` either way. The one field allowed markup is
`comment.content`, via `wp_kses_post()` — everything else is visitor input
landing in an HTML mail client. Unknown codes are left standing, not blanked (a
blank looks like an empty value). Our three render **per recipient**.

**The template** (`app/Views/email_template.php`) applies colours twice on
purpose: inline on the structure, and in a head `<style>` for pieces inside the
body that an owner can edit and we cannot reach inline. FluentAuth solves this
with a vendored Emogrifier — 60KB for a plugin with no autoloader, to style
markup we already control, so **do not add it**. `Mailer::setDefaultHeaders()`
leaves From/Reply-To empty unless set, so `wp_mail()` still decides by default.

## Frontend

**Svelte 5** (`resources/js/`) — `app.js` mounts to `.fluent_dynamic_comments`,
hydrating from the `data-bootstrap` JSON. Runes syntax. `ajax.js` is the single
XHR client; `session.js` memoises and calls `invalidateSession()` after each post
(tokens are single-use); `validate.js` mirrors
`CommentSubmission::validateIdentity()` and never decides.
`CommentBlock.svelte` recurses, gated on `maxDepth` — **mirrored by
`renderCommentList()`**.

**Vue 3 admin** (`resources/admin/src/`) — Element Plus, jQuery AJAX to the
`fluent-comments-admin-` prefix, config on `window.fluentCommentsVars` (the
frontend's is `fluentCommentVars`). Three tabs on `vue-router` hash history; each
page owns its save button, because one global button would post an untouched
page's state over another tab's write.

- **`WpEditor.vue` must tear TinyMCE down on unmount** — its global registry is
  keyed by element id, so a leftover entry means the next visit initialises onto
  a dead node and renders nothing. Content is read back on `change`, `keyup`
  **and** `SetContent`; `change` alone (what WordPress binds) fires only on blur,
  so a body typed and saved without clicking away saved empty.
- **`$syncToggles()` is load-bearing.** Settings still POSTs the whole
  `discussion` object, so without folding the response's fresh `toggles` back in,
  switching a core email off under Emails then saving Settings undoes it.
- **wp-admin's `forms.css` beats Element Plus on specificity**, so `style.scss`
  resets it scoped under `#fluent_comment_app` (1,0,0). If a new Element Plus
  component looks doubled, add its inner element there, not `!important`.
- **An `--el-*` token another plugin sets on `:root` is ours to answer.** A few
  Element Plus components paint from tokens the library only declares on some
  *other* component - a radio button reads `--el-button-text-color`, which is
  declared on `.el-button` alone - so they inherit whatever the page happens to
  set. FluentCRM's admin bar search script puts that one on `:root` as white
  from a `<style>` it appends on **every** wp-admin page, which left the
  unselected half of an email's two-way switch white on white. Both
  button tokens are answered on `#fluent_comment_app`; declare a token there,
  not a `color`, or the rule beats Element Plus's own checked state.
- All styles prefixed `flc_`, no scoped-style blocks, no webfont.

**Light / dark** — `theme.js` implements the Fluent theme mode spec, shared with
every other Fluent plugin on the same origin, so none of it is ours to change:

| | |
|---|---|
| `localStorage['fluent_theme_mode']` | `light` \| `dark` \| `system:light` \| `system:dark` |
| `<body class="fluent_theme_dark">` | present only while dark; light adds no class |
| `<html class="dark">` | Element Plus's own API; also carries `color-scheme: dark` |

Every `--flc-*` token is declared on `:root` and re-declared under
`body.fluent_theme_dark` — (0,1,1) beats (0,1,0), so dark wins with no
`!important`. **A literal hex is a bug.** `system:dark` caches the last
media-query answer and `applyStoredTheme()` repaints before mount, avoiding a
white flash. The email editor and preview iframe stay white in both themes: what
is edited is a light HTML email, and the furniture around it is WordPress's.

**React block** (`resources/block/`) — `save: () => null`, fully server-rendered.
Its editor preview's title defaults match `Frontend::getStrings()` exactly.

## Translation

**No reader-facing string is written in a `.js`, `.vue` or `.svelte` file without
going through one of these.**

| Layer | How | Reaches PHP via |
|---|---|---|
| Vue admin | `$t('English string')` | `TransStrings::getStrings()`, generated |
| Svelte frontend | `i18n.some_key` off `fluentCommentVars` | `Frontend::getStrings()`, hand written |
| Block | `__()` from `@wordpress/i18n` | `wp_set_script_translations()` |

The domain loads on `init` via `registerTextDomain()`; without it only
translations WordPress.org installs into `WP_LANG_DIR/plugins` resolve, never a
bundled `.mo`. In the Vue admin the English string *is* the key, falling back to
itself, so a missing translation shows English rather than a raw key.
`npm run i18n` scrapes every `$t()` / `$_n()` call into `TransStrings.php` —
**generated in full, never edit it** — because `make-pot` cannot read a `.vue`
file. `npm run build` runs it first, so a forgotten run cannot ship.

**Keep a sentence one string.** Markup goes in as `%s` and renders with `v-html`;
a button cannot be spliced that way (its handler would not wire up), so give the
button a label that reads alone and put the explanation beside it. US English, a
real `…`, product names never translated. Block strings live in the *built*
bundle, so build before regenerating the `.pot` (`./build.sh --pot` does both).

## Build & Release

Two pipelines into `dist/`: **Vite 6** → `dist/js`, `dist/css`;
**@wordpress/scripts** → `dist/block`. `emptyOutDir: false` because both write
there; `build.sh` clears it instead.

**One Vite pass, two entries** (`app.js`, `admin_app.js`), which share nothing
and so produce no chunk. There used to be a second pass: a separate front end for
classic themes shared `ajax` / `session` / `validate` / `autosize` with `app.js`,
Rollup hoisted them into a chunk, and WordPress enqueues these as plain script
tags with no `modulepreload` — a second serial request on every page with
comments, to share code between two front ends that were never on the same page.
Both themes load the same app now. **If you ever add an entry that shares a
module with another, that chunk comes back** and Rollup has no option to
duplicate instead; it needs its own pass.

`./build.sh` zips into `builds/`. `PAYLOAD` is a whitelist — anything new in the
repo root is left out and reported. A version mismatch between the plugin header,
`FLUENT_COMMENTS_VERSION` and the readme's `Stable tag` is fatal, not a warning.

## Key Patterns

- **Gating:** `Helper::isFluentCommentsPostType()` — reads `post_types` from
  settings.
- **Reading comments:** `CommentsRepository::getPayload()` — used by both
  `fluent_comment_list` and the server-rendered bootstrap, so they cannot drift.
- **Settings:** `_fluent_comments_settings` (defaults `post_types: ['post']`,
  `reject_native_comments: 'yes'`). Email content and template design live in
  `_fluent_comments_email_settings`; the on/off switches do not — see *Emails*.
- **Core Discussion settings** (`DiscussionSettings`): a chosen handful of
  WordPress's own options, read and written **in place**, never copied (excluding
  `require_name_email`). Core enforces them whatever form a comment came from, so
  this screen and Settings › Discussion cannot disagree. `update_option()` runs
  `sanitize_option()`, which trims and dedupes the word lists — which is why a
  save returns a fresh `DiscussionSettings::get()` and the UI replaces its state
  with it rather than keeping what was typed.
- **Branding:** the product is **FluentComments**, one word, everywhere a user
  sees it. `fluent-comments` stays the slug, text domain and shortcode prefix.
- **CSS theming:** public styles use `--fcom-*` in `resources/sass/app.scss`,
  overridden per-instance by the block's inline styles. The admin uses `--flc-*`.
- **`Arr` helper:** dot-notation array access for safe settings retrieval.
